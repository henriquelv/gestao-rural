Contexto do sistema

O que foi analisado

Sistema: app mobile de gestão rural, com cadastro de anomalias, comunicados, melhorias, instruções, dados de produção e mídia offline.

Risco técnico: o app é offline-first e sincroniza com Supabase. Por isso, smells em sync, armazenamento local e mídia podem afetar perda aparente de dados.

Escopo: services, screens, components e migrationsSlide 2
Métodos de identificação

  • Análise manual dos fluxos críticos: sync, banco local, telas de cadastro e mídia.
  • Busca textual com rg por padrões como any, localStorage, window e nomes de tabelas.
  • Contagem de linhas para localizar classes/componentes grandes.
  • Comparação de trechos parecidos entre telas de cadastro.

Smell 3

Uso excessivo de any

services/localdb.ts:22-35
export const localdb = {
  async getAll<T>(tableName: string, orderBy?: string): Promise<T[]> {
    // @ts-ignore
    const table = webDB[tableName];
    const records = await table.toArray();
    let data = records.map((r: LocalRecord) => r.data);
    if (orderBy) {
      data.sort((a: any, b: any) =>
        (a[orderBy] > b[orderBy] ? -1 : 1)
      );
    }
    return data;
  }
}

Por que é smell: any e @ts-ignore reduzem a proteção do TypeScript. Erros de campo, tabela ou payload podem aparecer só em runtime.

Solução: criar um mapa de tipos por tabela: TableName, TableRecordMap e métodos getAll<K extends TableName>(table: K).

Impacto: bugs de schema e sincronização passam despercebidosSlide 7

Por que é smell: flags globais, eventos em window e localStorage.clear() tornam o comportamento difícil de prever e testar.

Propostas de melhoria

Plano de refatoração recomendado

  • Extrair tableRegistry central para regras de sync e banco local.
  • Dividir SettingsScreen em painéis menores.
  • Transformar processItem em handlers por tabela/operação.
  • Substituir any por tipos de domínio e mapa de tabelas.
  • Criar hooks comuns: funcionário, mídia, payload com farm_id.
  • Registrar erros em tela de diagnóstico em vez de apenas retornar null.
  • Trocar localStorage.clear() por limpeza controlada.
  • Remover migration duplicada e evitar PIN fixo em SQL.
Foco: reduzir risco sem mudar comportamento do appSlide 13
Conclusão

Principais aprendizados

Os smells encontrados não significam que o sistema está “errado”; eles indicam pontos onde a manutenção ficou mais arriscada. Em um app offline-first, smells em sync, estado local e tratamento de erros têm impacto direto na confiança do usuário.
